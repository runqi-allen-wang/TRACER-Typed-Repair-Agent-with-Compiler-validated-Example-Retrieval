# LeanCapsule Challenge Pilot

> Generated from an actual run by `scripts/summarize_capsule_challenges.py`. The measured table and counts must not be edited independently of the JSON result.

## Purpose and isolation

This feasibility pilot measures current theorem-based LeanCapsule behavior on four deliberately small boundary cases. It is the challenge companion to the 12-case core gate and remains separate from the public gallery release audit: fallback, diagnostic drift, and replay failure are retained as measured challenge outcomes.

The combined core/challenge result is generated by `scripts/run_capsule_feasibility.py` and documented in `docs/CAPSULE_FEASIBILITY.md`.

## Case design

- `same_file_dependency` (same-file preceding declaration dependency): Change the expected result of normalizeNat 1 from 2 to 3. Expected: The rfl proof fails while normalizeNat remains available in the full source.
- `project_local_multifile` (project-local multi-file dependency): Change the expected result of localBump 1 from 2 to 3. Expected: The rfl proof fails after importing the locally built Challenge.Helper module.
- `multiple_diagnostics` (multiple diagnostics from one propagated tactic mutation): Replace the shared assumption tactic with rfl after the <;> combinator. Expected: The single tactic mutation is applied to both generated goals and should emit multiple diagnostics.
- `complex_local_context` (implicit parameters, type class coercion, and local context): Replace the equality hypothesis h with the coerced source term x. Expected: Lean reports a type mismatch in the theorem's implicit and coercion-sensitive local context.

Every case has a compiling `Correct.lean` and an `Error.lean` differing on exactly one source line. Every error is packed with `--theorem`.

## Interpretation and next priority

No clean-replay blocker remains. Dependency-aware extraction is still an optimization opportunity because fallback was required for `same_file_dependency`, `project_local_multifile`. The strict observation should remain an analysis layer for later diagnostic-fidelity work.

The strict metric compares the complete ordered diagnostic text after normalizing paths, line/column locations, metavariable identifiers, and trailing whitespace. It is explicitly a challenge-analysis observation: text equality is not semantic equivalence, and this metric does not replace the current official status/category/`diagnostic_key` criterion.

## Scope limitation

This is a four-case feasibility pilot. It exposes concrete behavior in these fixtures only and does not prove general LeanCapsule feasibility, diagnostic equivalence, or robust project dependency capture.
