# Lean 编译反馈与 SP-n 后续工作方案

> **状态：repair24 正式六臂批次、DeepSeek Pro/Flash 反馈表示研究与 SP v2 均已脱敏发布（2026-09-21）；SP 隔离协议已于 2026-09-24 发布首份 Linux 实测。** 六臂发布包覆盖 864 个任务、1,066 条有效轮次和 811 个独立复编译成功证明；预注册主比较 R-B−R-A 在 Flash 为 0.0 个百分点、在 Pro 为 −2.8 个百分点。结果只支持同一供应商模型族、24 道独立题上的描述性结论，不能证明普适或因果增益。SP 的 Linux 报告观察到 14/14 项冻结控制，但 Windows Docker Desktop 尚待完成，因此不构成双平台沙箱证据。

Community feedback from [subfish-zhou](https://github.com/subfish-zhou) and [Fulcrum-Nebula](https://github.com/Fulcrum-Nebula) motivates two next-stage tracks: measuring how models use Lean diagnostics, and expanding SP-1 into a versioned SP-n security program. The plan below freezes evidence boundaries before implementation.

## 1. 总体原则

1. **先做离线门禁，再调用模型。** 诊断抽取、协议快照、题库冻结和安全案例必须先由本地测试通过。
2. **不回写旧实验。** 新协议、新提示或新安全规则使用新版本和新输出目录，不补写现有轨迹。
3. **不让运行器读取参考证明。** 参考答案仅用于测试和独立复编译，不能进入 prompt、检索语料或反馈转换。
4. **基础设施错误单列。** provider 错误、工具链缺失和超时不能算作普通证明失败。
5. **付费运行另行授权。** 本方案本身不调用 API；模型、任务数和费用上限必须在运行前单独确认。

## 2. Track F：研究 Lean 编译诊断反馈

目标不是简单回答“有没有反馈”，而是判断：哪类反馈被模型正确理解、下一轮是否处理了对应错误，以及额外上下文是否值得其 token 和时间成本。

### F0：冻结基线

**当前进展：当前 DeepSeek 批次已完成。** `tracer-compiler-feedback-v1` 以可读全文快照冻结诊断规则与 15 个夹具；Feedback Study v1 另行冻结 repair24、三表示、三重复和模型参数，没有改写旧实验。后续跨模型复现必须新建配置与输出目录，不得回写当前批次。

**任务**

- 固定 repair24 版本、Lean 工具链、模型参数、最多轮数和编译时限。
- 保留 R-B、R-E、R-F 的现有含义；新反馈表示不得静默替换这些组。
- 保存 prompt 模板、诊断转换规则和题目全文快照。

**交付物**

- 新协议版本说明。
- 只读实验计划和调用预算预览。
- 检查题目、检索语料及参考证明隔离的离线测试。

**验收门禁**

- 计划可在不联网时完整生成。
- 旧轨迹和旧报告逐文件不被修改。
- 每个任务的原始错误能由 Lean 稳定重现。

### F1：建立可审计的反馈表示

**当前进展：离线实现已完成。** [Compiler Feedback v1](COMPILER_FEEDBACK_V1.md) 同时保留原始、规范化和结构化三层；每个类别和结构化信号都必须保存可在脱敏原文中逐字定位的证据片段。12 个真实 Lean 失败与 3 个基础设施事件由 CI 离线复验。

为每次编译同时保留以下三层信息：

1. 原始 Lean 输出，仅做路径和凭据脱敏。
2. 当前归一化诊断，保留错误类别、位置、消息和目标。
3. 结构化行动字段，例如未知标识符、期望/实际类型、未解决目标和 instance/elaboration 线索。

结构化字段必须由编译输出产生，不能利用参考证明。每个转换都保留来源片段，方便人工检查是否压错或漏掉关键信息。

**最小错误类型覆盖**

- 未知标识符或命名空间问题。
- 类型不匹配与函数应用错误。
- 未解决目标。
- 语法错误。
- elaboration 或 typeclass instance 错误。
- 超时、provider 错误等非证明失败。

### F2：离线验证“反馈是否被采纳”

**当前进展：实现与本地单模型轨迹已完成，公开证据待导出。** [Feedback Adoption v1](FEEDBACK_ADOPTION_V1.md) 可逐轮区分候选不变、与诊断信号相关的修改、无法由词法规则判断的修改、缓存复用、反馈为空/转换失败和基础设施错误；同时分别汇总静态与诊断驱动检索的 query/Top-k 变化。本地 DeepSeek 批次已生成相关修改率和重复错误类别率，但这些仍是行为观察，不等于模型因果理解反馈。

在调用真实模型前，为错误转移分析补齐离线测试：

- 相邻轮次的错误类别是否变化。
- 新候选是否修改了报错附近或相关标识符。
- R-E/R-F 的检索查询与 Top-k 是否随诊断变化。
- 反馈为空、反馈压缩错误和模型未采纳反馈能否分开记录。
- 同一轮不能因缓存复用而伪装成新生成。

### F3：受控模型实验

**当前进展：DeepSeek 批次已脱敏发布并转入历史归档。** [Feedback Study v1](../historical/feedback_study_v1/docs/FEEDBACK_STUDY_V1.md) 使用独立协议比较 raw、normalized、structured 三组；repair24 × 三表示 × 三重复共 216 个任务已完成，199 个成功证明通过独立复编译和显式标注的 AI 辅助复核。发布包保留 283 条有效逐轮记录和传输重试计数，不公开逐请求完整 prompt 或失败归档原文。单模型结果不能推出跨模型效应。

建议建立独立的反馈表示子研究，不复用现有研究臂名称。最低对照为：原始诊断、归一化诊断、结构化诊断。三组必须使用相同题目、模型、顺序、轮数、输出上限和编译预算。

**主要指标**

- pass@1 与有界 pass@3。
- 每类错误从失败到成功的转移率。
- 下一轮仍重复同类错误的比例。
- 平均轮数、生成时间、编译时间和总时间。
- prompt、completion、total token 及已知费用。
- 检索查询和 Top-k 的实际变化率。
- provider/工具链基础设施错误数。

**解释规则**

- 先报告配对逐题结果，再报告均值。
- 小样本只作描述性结论，不写统计显著或普适增益。
- 若结构化反馈增加成本但没有改善错误转移，应如实保留负结果。

### F4：第二模型独立复现

**当前进展：DeepSeek Flash 模型族内复现已完成并转入历史归档，独立供应商复现未完成。** [第二模型复现协议](../historical/feedback_study_v1/docs/SECOND_MODEL_REPLICATION.md)通过 `--reference-release` 在付费请求前核对 Pro 发布包；公共题库、任务顺序、三表示、三重复、轮数、编译时限、温度、输出上限和静态模板均未漂移。Flash 的 216 任务、209 个证明、AI 辅助复核和脱敏发布包已通过门禁。

`scripts/compare_feedback_models.py` 已对齐 Pro/Flash 的 216 个任务，并报告首轮与最终结局一致率、各表示成功差和表示对比方向一致性。报告单列共同零差异，避免把“两个模型都未出现表示差”解释为处理增益复现。下一次独立供应商复现仍须披露 thinking/reasoning 接口、tokenizer、别名更新和服务端默认值等残余混杂。

### F5：正式六臂结果后的确认性研究

**当前进展：repair24 六臂矩阵已完成并发布，确认性外推尚未开始。** 当前结果没有显示 R-B 相对 R-A 的稳定正向差异；动态检索与失败 Capsule 的最高观测值也只出现在 Flash。后续不应通过重复运行同一批次追求更好数字，而应把以下三项作为新的、独立预注册：

1. 在 TRACER-REAL v2 的项目级 test 划分上复验同首轮候选分叉，主要估计按项目等权。
2. 使用独立供应商模型复现 R-A～R-F，避免把同一供应商的两个配置当成跨模型普适证据。
3. 把错误状态、路由决策、检索 query 与 Top-k 变化纳入逐题分析，解释“何时有效”，而不只比较总体成功率。

每个新批次使用新的预注册、输出目录和发布包；不得回写 repair24 六臂工件，也不得把重复和实验臂当成新的独立题目扩大样本量。

## 3. Track S：把 SP-1 扩展为 SP-n

SP 是安全策略编号，不是 R-A～R-F 之外的新增实验臂。新增编号前必须先写清威胁、正常对照和预期拦截位置。

### S0：冻结威胁模型

**当前进展：v2 已冻结。** `benchmarks/security/threat_model.json` 明确资产、攻击者能力、信任边界、范围外风险、案例、正常对照和正常对照的真实编译目标。该模型仅覆盖不受信任候选进入 Lean 编译前的边界。

每个候选 SP-n 案例至少记录：

- 攻击面与最小可复现 Lean 源码。
- 原生 Lean 在受控环境中的真实行为。
- 应在文本门禁、编译环境、资源限制还是操作系统隔离层处理。
- 允许通过的相似正常候选。
- 当前规则无法覆盖的残余风险。

### S1：扩充对抗案例

**当前进展：第二版离线套件已完成。** SP-1～SP-12 覆盖 unsafe 声明，环境/进程/文件/网络元编程入口，资源选项，import/axiom/#eval/macro 命令注入，以及 kernel-only 策略下的原生执行入口。除已受控验证的 SP-1 外，危险输入只验证“编译前拒绝”，不会为了演示而在主机上执行。

按风险而不是按关键词组织候选案例：

- unsafe 声明和显式元编程。
- 本机文件、进程、环境变量与网络访问。
- 资源耗尽和超时。
- imports、Lake 依赖与项目边界逃逸。
- 会被 Lean 接受但违反项目证明可信边界的构造。

新增案例先进入独立测试目录。通过人工复核并确认不会包含凭据或本机路径后，才能成为公开 SP-n 案例。

### S2：同时测量安全性和可用性

**当前进展：冻结案例指标与确定性发布已完成。** `src/security_study.py` 同时报告危险案例误放行、正常对照误拒绝、正常对照真实编译、检测器一致性和拒绝前是否调用编译器。当前套件结果为 0/12、0/8、0/8、0/12、0/12；误放行与误拒绝的 Wilson 95% 上界约为 24.3% 和 32.4%。样本很小，且不能代表未知攻击。

安全报告必须同时列出：

- 恶意候选被放行的数量与原因。
- 正常候选被误拒绝的数量与原因。
- 拒绝发生在哪一层。
- 编译是否在拒绝前已经启动。
- 超时、内存或进程限制是否真实生效。

只证明一个已知攻击被拦截，不足以声称系统安全。

### S3：增加操作系统级隔离

文本规则和清理后的子进程环境都不是完整沙箱。应在独立分支验证容器或低权限账户方案，并明确：只读源码范围、可写临时目录、网络策略、进程与资源限制、超时后的清理方式。Windows 和 Linux 的实现与证据分别记录，不能用改环境标签代替真实运行。

**当前进展：原型、离线门禁与原生 Linux 首次实测已完成，真实双平台结果未完成。** [SP 容器与低权限隔离协议 v1](SP_ISOLATION_V1.md)冻结 Linux Docker、非 root UID/GID、只读根文件系统与仓库、独立 noexec `/tmp`、禁网、清空 capabilities、`no-new-privileges`、seccomp 以及内存/CPU/PID/墙钟限制。[Linux 发布包](../published/security-isolation-tracer-sp-v1/)保存 GitHub-hosted Ubuntu Docker Engine 的 14/14 控制实测；普通 CI 审计已提交报告，手动 workflow 才生成新的真实容器证据。Windows Docker Desktop 尚未实测，因此不能升级为完整双平台隔离结论。

## 5. 第一轮可以立即开展的工作

以下工作不需要 API，也不会改变已有结果：

1. **已完成：** 为现有诊断类别冻结 15 个最小失败夹具，其中 12 个由 Lean 真实编译、3 个为显式基础设施事件。
2. **已完成：** 定义原始、归一化、结构化三层反馈记录与 JSON Schema，并要求每个结构化字段保留原始诊断片段。
3. **已完成模型族内复现：** 记录错误类别转移、候选相关修改、反馈缺失/转换状态、缓存复用和检索 query/Top-k 变化；Pro/Flash 脱敏发布与逐任务配对已完成，独立供应商仍待完成。
4. **已完成第二版：** 冻结 SP 威胁模型、12 个危险案例和 8 个可真实编译的正常对照，并同时报告检测器一致性和带 Wilson 区间的双向错误率。
5. **原型与 Linux 首次运行已完成：** Windows 与 Linux 共用的 Docker 低权限探针、14 项冻结控制与手动工作流已实现；Linux 14/14 实测已脱敏发布，仍需 Windows Docker Desktop 报告。单平台结果不宣称完整沙箱。

下一阶段按以下顺序推进：严格按已冻结的 TRACER-REAL v2 对象开展项目级确认实验，再进行独立供应商复现；SP 线补齐 Windows Docker Desktop 报告并与已发布 Linux 报告逐字段比较。三条线使用独立工件和门禁，任一计划或中间状态都不得写成已完成结果。
